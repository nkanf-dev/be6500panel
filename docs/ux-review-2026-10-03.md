# be6500panel 用户视角 UX / 功能审计 — 2026-10-03

## 1. 结论与审计边界

面板已经不是纯静态样机：有真实读取、六包 UCI 事务、sing-box/frpc 运行管理、有限订阅编译和单客户端接管代码。但“有原生编辑入口”“进程 running”“规则创建成功”和“官方路由器功能已完成”是四件不同的事。当前用户最容易遇到的问题是：

1. 普通设置仍需读写原始 UCI；字段视图只读，跨页面编辑容易丢失。
2. 状态语言比实际功能更完整；进程、配置、计划、运行核验之间缺少明确分层。
3. 首次使用代理有隐藏前置条件，出错后不知道下一步在哪。
4. 历史和分析图表的持久采集不足；大部分分析仅有明确标记的 demo 图。
5. 几条恢复/并发路径有实际安全缺陷，不能靠“已回滚”“接管中”字样视为通过验证。

**基线：**工作树起点 `b04f55f16bb8b21e2bc3d4904910233e8c947e65`。下面的行号主要指这个基线；本次明确标为“已修”的代码会移动行号。

**范围：**读取全部当前应用路由、UI 模块、共享表单/图表、API 合同，以及 `internal/httpapi`、`modules`、`router`、`control`、`runtime`、`proxy`、`capture`。同时对照 `docs/official-capability-matrix.md` 和 `docs/superpowers/plans/2026-10-03-durable-history-and-usability.md`。

**验证边界：**仅本机源码、离线单元测试、mock API 和 `--demo` 浏览器测试。未访问 RN02，未 SSH，未启动实际或合成 TAP 客户端接管，未改路由器配置。后端问题是已确认的代码路径缺陷，不是本次复现的现场故障。截图已生成，但当前模型不支持看图，因此视觉审查不列为证据；DOM 与 viewport 测试可以列为证据。

**优先级：**P1 = 数据丢失、错误生效、恢复/管理路径风险，优先修；P2 = 常用工作流阻塞、误导状态、重要能力缺口；P3 = 一致性、便利性、低风险鲁棒性。这里没有给尚未复现的现场事故标 P0。

**并行边界：**其他工作树正在处理历史、设备/接管 UI、配置字段表单、遥测和控制安全。本报告不把“已分配”当作“已完成”，也不证明其他工作树的实现。已修项仅指本审计分支实际提交和测试过的修改。

## 4. 剩余前端 / 常用工作流问题

### F06 — P1：换页、换“观察”标签会丢失未暂存文本

证据：`ConfigurationEditor.tsx` 每次新建 `useConfiguration()`；`use-configuration.ts:40` 明确页面独立持有 buffers；`unavailable.tsx:57-65` 与 `network.tsx` 通过条件渲染卸载编辑器。`app/pages.tsx` 换模块也卸载。runtime native editor 与代理导入表单同样局部保存。

用户路径：改 SSID → 点击“观察”确认当前状态 → 回“配置”，未暂存修改消失。已有“切换文档保留编辑”测试仅证明同一个 `ConfigurationWorkspace` 内部切文档，不证明跨页。服务端暂存草稿可能仍在，但编辑器回显的是 saved document；没有从草稿恢复可编辑文本的动作。

建议：认证会话内共享内存编辑 buffer；切页/切标签统一 dirty 提示；提供从选中草稿恢复编辑。不要把私密原文默认落 browser storage。最小验收：Wi-Fi 改值、切观察/网络/返回、保留；退出登录清理；未保存刷新明确警告。

### F07 — P2：配置默认打开原文，“字段视图”也只读

证据：`NativeEditor.tsx:23` 默认 `editor`；`:217-240` 只是 `<code>{field.value}</code>`；章节导航和行号很完整，但没有真实输入。DNS/Wi-Fi/网络常规页面都指向这个编辑器。

影响：用户想改 Wi-Fi 名、DHCP 地址池、DNS、MTU，必须先理解 UCI option/list、section 类型、引号与跨包引用。表面“字段视图”不能完成最普通设置。章节或当前值不能点击进入带上下文编辑。

建议：常用字段默认类型化表单，原生专家编辑另列入口。基于实际 adapter/schema/允许枚举，保留未知厂商字段；不从通用 OpenWrt 模板推测 RN02 radio/端口。字段视图如果仍只读应叫“字段检查（只读）”。验收不仅是输入可改，还要差异、校验定位、实际适配器生效/读回与恢复。

### F08 — P2：选中草稿、当前编辑、提交结果的关系不够可见

证据：`use-configuration.ts:108-121` 初次进入自动选每模块最新有效草稿；`CommitControls.tsx` 顶部只显示数量，低风险可直接 Commit；`DraftQueue.tsx` 差异在底部，旧/无效草稿只允许看差异和删除；`native-document.ts` changed fields 只用于高风险弹窗。

风险不是“暂存会生效”（当前代码明确不生效），而是用户打开另一模块后可能带着别的历史暂存选择一起提交，不清楚当前未暂存内容不包含在 Commit 中。提交后的 operation 只在当前 controller 内；重进页面没有最近操作终态。

建议：Commit 条展示文档名/变更摘要/选中版本，明确“以下草稿会生效；当前未暂存文本不会生效”；选中应是意图，不跨页面悄悄继承；能恢复草稿编辑、替代/清理旧草稿；最近提交/回滚结果可读，不只有“暂存队列”。

### F09 — P1/P2：高风险变更后缺少全局重连与确认任务

证据：pending 确认 UI 仅在 `ConfigurationSurface` 中；`use-configuration.ts:185-192` 只有该 editor 挂载时轮询；`CommitControls.tsx` 显示倒计时和 Confirm/Rollback，但没有新管理地址、无线重新连接、固定可读 job URL、离线后恢复指引。

用户可以提交 LAN IP/主 Wi-Fi 改动后去概览，确认入口从眼前消失，120 秒后回退；若连接已中断，浏览器只自动重连旧 origin。后端超时/重启恢复仍存在，不能说没有任何恢复。

建议：全局 pending 操作条、可恢复的任务路由/ID、实际新地址和本机重连步骤、明确确认条件与截止时间；离线期间不能假定已回滚；恢复后展示权威终态。生产功能核验缺口见 B8。

### F10 — P2：保存配置和运行配置没有分离展示

证据：`RuntimeControls` 的 configured 只说“已验证”；`useRuntime` state/result 局部保存；`NodeSelector` 输入的 IPv6/ports 固定 defaults (`node-selector.tsx:32-38`)，GET nodes 只回选中 ID、不回已提交策略；`frpc.tsx:28` 每次打开空 initial form，不解析 saved TOML；原生 editor 载入需要另操作。

后果：已运行 frpc 用户返回“连接与映射”却看到空服务器/默认映射；sing-box 运行配置用 follow/自定义端口，UI 返回仍显示 direct/2080/7893/6450，下一次 Commit 会改回。frpc 成功后 token 清空且已明确警告空 token 会删除认证，这是已有诚实说明，但仍不能作为成熟编辑工作流。

建议：展示“已保存/已校验代际”“进程实际使用代际”“当前未保存输入”；已存在配置先读取或显示“新建（不代表已保存配置）”。部分解析不能无损 round-trip 时保留 raw 入口；凭据显示“已设置/保留”而不是空字段等于删除；改 token 用显式替换/清除。

### F11 — P2：部分错误/旧数据容易像当前正常状态

证据：`use-resource.ts` 失败保留 data；`network.tsx:89-129` 错误后仍显示绿色 UP 原表，不标“上次成功数据”；`runtime/controls.tsx` 同样保留 status；`use-runtime.ts:82` mutation error 优先于后续 observation error，成功刷新也不清前次 mutation error；`console-context.tsx:69-80` health 和 modules 共用 error，modules 成功可以清掉同时失败的 health 错误。RouterObservationFrame 已正确在 routerError 时不把旧 snapshot 当当前成功，这个做法应复用。

建议：分别持有读取错误和操作错误；每张表/状态显示成功读取时间与 stale；UI 未知≠false/未接管/无设备。重试只能重读，不盲目重放 POST。Runtime acquire 长达 7 分钟，当前没有进度/取消状态或断线后任务恢复，不能只让按钮长时间 pending。

### F12 — P2：生产分析和一年历史并未实现，不能让用户找不到“启用采集”

证据：`proxy/connection-analysis.tsx:40-44` 给图只传 demo boolean；`RequestWaterfall`、`LatencyDistribution`、`RuleHitChart` 与 `ActivityHeatmap` 只引用 `demo-data.ts`，无生产 API。ChartFrame 在 demo=false 时为空，所以**未发现生产填假数据**；问题是“未接入”不区分功能待实现、没启用、没权限、当前无流量、查询失败。

历史基线：`console-context.tsx:155,199,222` 浏览器隐藏就停止采样、最多 300 点；`TrafficTrend.tsx:20,34,41` 又截 300 点并用 category axis，失联/后台间隔会连成连续曲线；真实图用“最近 N 点”而不是用户时间范围，没有 rxBytes/txBytes/coverage/持久性/留存说明。WAN fallback 使用名称猜测 (`console-context.tsx:175-178`)，不能替代准确默认路由接口。最初零速率是“尚无第二计数”的含义，不是已测 0。

建议：按已写 durable-history 计划实现服务端持续采集、400 天有界多分辨率存储、真实 counter delta 字节总量/coverage/gaps；八个时间范围；注明开始记录时间，不假称已有一年。图表区分明确待实现 vs 配置缺失 vs 暂无数据/错误；返回时间戳以 time axis 保留间断。其他工作树负责，本分支未验证其结果。

### F13 — P2：模块名/描述比观察数据更丰富

证据：`modules/registry.ts:74,84,94` 是“客户端与设备策略”“无线接入与射频状态”“解析路径与分流策略”。实际 devices 是租约/ARP，Wi-Fi 是 UCI configured fields，DNS 是 resolver 地址和 leaseCount，Firewall 是两行默认策略/总规则数 (`router-devices.tsx`、`router-wifi.tsx`、`router-dns.tsx`、`router-firewall.tsx`)。

已有细节说明是好的：ARP 不等同在线，配置信道不等实际射频，rule count 是总数。但是首页就绪数/能力列表仍给出“路由器全域健康”的视觉印象，unsupported capability 只有弱化颜色、没有明确“不支持”文字 (`overview.tsx:204-226`)。

建议：模块 header 如“无线配置观察”/“客户端租约与 ARP”，能力按读取/编辑/运行核验/未实现分开；未知、disabled、不适用、planned 不要都变未接入。真实射频/终端功能要 dedicated adapter，不靠改标题实现。

### F14 — P2/P3：诊断不足以帮助普通用户恢复

证据：LogsPanel 只 `GET /logs?limit=100`，内存缓冲、手动刷新，无 native core stdout/stderr 流、系统日志分页/下载、失败 job 详情；API 多为通用“配置校验失败，请查看运行诊断”，但对应底层诊断不一定有可查入口。很多 code/recoveryPlan 是英文内部步骤。`lib/format.ts:15` 日志只显示时间、不显示日期，多日诊断易混淆。

建议：code 保留但解释“发生了什么/配置是否已保存/进程是否改变/下一步”；状态码映射一致；日志按模块/任务可跳转、有日期/时区、认证下载与有界容量说明。native checker 错误需结构化安全投影，不是让用户 SSH 才能知道错误。

### F15 — P3：入口/标签/可访问性一致性仍不完整

- System 只从 hash 读取 diagnostics，其余 tab 都局部 state；back/refresh 不能恢复原生配置/changes；proxy/frpc 和 router tabs 也没有 deep link。证据 `system.tsx:31-63`、`router-view-tabs.tsx`。
- 多组 tab 有 role=tab，却缺 `tabpanel` 对应/roving keyboard arrow navigation；FRPC 当前有 id/aria-controls 是局部较好的实现。Button 禁用无具体原因应伴随 helper，而不是仅视觉灰色。
- Cmd+K 目前只导航与主题；“搜索模块与操作”不包含具体设置/设备/恢复任务。可以先改诚实名称，再加可发现的具体任务，不能做假命令。
- Demo 标记明确，但 network 仍观察本机真实接口，router 读取本机来源而不是完整 RN02 fixture；需要“演示系统 / 当前宿主网络”来源分区，避免截图误以为一台真实 BE6500 全部数据。
- 390px 手机现有 browser 测试通过，但主要覆盖系统页。不代表所有原生编辑器/长风险弹窗/代理节点表可用；应加普通表单和 pending 流程手机测试。

## 5. 后端对用户结果有实质影响的缺陷

下面保留独立后端审计编号 B1–B18，方便分配和验证。源码只读审查已确认路径；没有声称现场出现。特别是 B1/B2 应先离线 fixture 测试修复，再考虑配置操作。

### B1 — P1：一次超时回滚失败后，自动回滚 worker 永久退出

`internal/control/manager.go:775-783` 在 deadline rollback 错误时 `return` 整个 deadlineLoop。worker 只在 New 启动一次 (`:123`)。手动 Rollback 成功 (`:734-744`) 清 recoveryError，后续再次可以 Commit，却没有重新启动 worker。第二次高风险 Commit 的 UI 仍给截止时间，但无人自动回退。

修复：错误进入可恢复状态但保持 worker 存活，防止忙循环；成功手动恢复后可重新处理后续 deadline。验收：timeout → reload 故障 → manual recovery → 第二个不确认的 risky commit，仍自动回滚。

### B2 — P1：防火墙风险识别漏掉实际管理拒绝规则和厂商 include 删除

`internal/control/validate.go:409-419` 只比较 defaults/zone policy string，deny rule 只在 src_ip 或 dest_ip 有一个为空时计风险。针对管理员源 IP + 路由器目的 IP/8787 的精确 DROP/REJECT 同时有两者，反而不在风险集；zone 的 network/device membership 也不比较。`manager.go:521-526` 按 risks 决定是否 provisional，因此可能直接最终提交。

另：`validateExecutionChanges` (`validate.go:556-575`) 只检查新增/改变 include；删除既有 vendor include 不报错，且 `firewallFields` 也看不到它。注释说 preserve factory includes，实际未保证。

修复：管理可达性相关规则/区域范围保守进入 provisional；不可通过更精确规则绕过；厂商 include 拥有者不允许 raw 文档删除/替换。fixture 测覆盖精确双 IP deny、zone membership 改变、include 删除及既有正常规则不误改。

### B3 — P1：capture / UCI / runtime 没有设备级原子写通道

三套独立锁：`control/manager.go:431-433`、`capture/capture.go:100-105`、`runtime/manager.go:188-212`。`httpapi/configuration.go:75-78,151-159` 撤接管后释放 capture 锁才 Commit，另一 capture POST 可在 reload 中重装。`proxy_capture.go:37-65` 在 Apply 之前单独检查 running，与 Stop/进程退出 cleanup 不是同个事务；检查后核心停止，Apply 仍可能装到死核心。

修复：一个明确的 device write ownership / coordinated lane，把“前置验证→必要清理→生效→核验”放同边界；不能只给 HTTP handler 加互不共享的锁。接受并发 fixture 测，不执行实际网络接管。

### B4 — P1/P2：代理绑定、接口和 router DNS 地址写死

`proxy_runtime.go:197-201` 使用 `192.168.31.1` mixed/IPv4 DNS/management；`proxy_capture.go:64` 使用 `br-lan` 和旧地址。用户通过支持的 LAN 原文修改后，生成配置可绑定不存在的地址，capture 接错接口，router DNS 映射错。IPv6 follow 用 `::`，却未使用真实 IPv6 router DNS 地址。

内核 LOCAL bypass 仍保护其他 local 管理目的地，不应夸称所有管理流量都会被接管。具体缺陷是 bind/interface/DNS mapping。

修复：当前拓扑发现和 typed LAN identity，生成配置与 capture 从同一接受状态取地址；不支持拓扑应拒绝并明确原因，不能默认 factory 值。单元 fixture 覆盖非默认 LAN/IPv6。

### B5 — P1：选中节点元数据与实际 runtime config 可能分离

`proxy_runtime.go:211-224` 先 Configure（可能重启），后写 `proxy-selection.json`。落盘失败/accepted config 已更新后 start 失败，可保留旧节点/ports/endpoints。`runtime.go:54-67,110-122` 原生 Configure/Restore 不更新 selection。capture (`proxy_capture.go:50-64`) 只比 IPv6 字符串，不比配置 hash/generation/listeners/节点。导入只清内存 selected (`proxy_runtime.go:102-111`)，旧 selection 文件可在重启再次读入 (`:41-46`)。

修复：接受的配置代际/hash/节点/监听/端点一个 manifest；capture 只使用一致性已确认的 manifest；原生编辑/恢复或新订阅须使旧选择无效。不能让“已选择”替代“当前进程正用这个配置”。验收覆盖 metadata 写故障、native configure/restore、重新导入再重启。

### B6 — P1/P2：不支持规则被 API 自动同意丢弃

`proxy_runtime.go:149-159,201` 没有用户 acknowledgment 字段，却硬编码 `AcceptUnsupportedRules:true`，绕过 `proxy/native.go:96-103` 的显式确认要求。用户订阅内某些 block/direct 规则不生效，却可能得到“explicitly acknowledged”输出。

修复：先返回准确影响预览；必须用户明确同意不支持规则被舍弃，或者拒绝 Commit。后端/前端合同需同步，不只在日志加警告。验收未确认不 Commit；确认具体影响后才允许。

### B7 — P1：runtime 写失败响应隐藏“配置已经接受”的部分成功

runtime manager 在 ErrDurability (`runtime/types.go:29-31`、`manager.go:431-445`) 或接受后启动失败 (`:447-451`) 返回真实新 status/generation；`httpapi/runtime.go:124-128,133-158` 对任何 error 丢弃 status，并把 durability 变 generic 500。用户以为提交未发生，重试才发现 generation conflict。

Live Configure/Acquire 会先停旧核心，新 readiness 失败并不自动恢复旧运行 (`manager.go:372-376,447-451,642-651`)；LastGood 是上个 accepted config，不保证健康。这后一项是恢复工作流不完整，不是校验器接受了错误语法。

修复：结构化区分 rejected / accepted-not-durable / accepted-but-not-running；携带权威 generation/status；提供已知旧配置恢复并核验，无盲重试。适配 UI 显示已保存≠已生效。

### B8 — P1：已回滚没有核对回滚文件一致性，生产功能验证 hook 未接入

`control/manager.go:688-738` 写回、reload 后 fingerprint 当前任意内容就标 rolled_back，没有比较 Before，也没调用 Verify。reload 返回成功但重写了恢复文件也会宣称恢复成功。生产 `cmd/be6500panel/main.go:106` 没给 Verify，`manager.go:403-412` 无 hook 直接通过；普通 commit 只检 candidate bytes (`:414-418`)，Confirm 重复 no-op Verify (`:630-637`)。

必须准确说当前“committed”主要表示文件接受 + reload exit success + 风险变更 HTTP 确认，不是 WAN/DHCP/无线/防火墙功能已验证。

修复：回滚文件 compare 必须成功；实际 adapter 支持的运行核验明示/执行，未实现只能标“文件已恢复，运行未核验”；不要让失败 fallback 宣称完全恢复。

### B9 — P1/P2：超时恢复失败后，重连可能拿不到恢复操作 ID

`control/types.go:74-79` / `manager.go:169-172` Status 只有 generation/pending/error。rollbackLocked 先 phase=rolling_back (`:682-685`)，pending() 不再返回 ID (`:163-167`)，失败时 error 保留但 ID 消失。若浏览器从未拿到原 Commit 响应，重连后需要 Rollback ID (`httpapi/configuration.go:101-110`) 却拿不到，Documents/Drafts 也被 recoveryError 阻止。

修复：Status/API 可读 active/recovery operation、phase、ID、可用动作；重连能安全 retry recovery，不查 private journal 才能恢复。

### B10 — P2：被拒绝的 Commit 也先撤销正常接管

`configuration.go:75-78,151-159` 在 generation/drafts/no_changes/risk 校验前 Cleanup；manager validations 是 `:438-494`。一个 stale/malformed intent 可让代理客户端失去接管，虽然任何 UCI 变更未接受。

修复：只在已验证、原子生效边界撤；响应说清是否撤了接管，不让“提交失败”隐藏副作用。

### B11 — P2：capability / 旧状态 API 与当前 adapter 相互矛盾

- 部分**已修**：runtime 已启用却仍说 not integrated，见 F02。
- **未修**：`modules.go:13-19` router pointer 存在就 ready，不反映各来源错误。`server.go:174-186` `/api/devices` 永远 supported=false/空，`/api/frpc` 永远 supported=false/running=false，虽然 `/router`、`/runtime` 有真实数据。`modules/network.go:15,25` 说路由 adapter 未接入，但 router 已有 routes。
- `server.go:150-155` health.readOnly 只看 control；只启 runtime 仍可配置/启停进程，却说 readOnly。F01 已把 UI 限定为“配置只读”，API 本身没有完整 capability 模型。

修复：废弃重复旧端点或代理到权威域状态；能力发现、来源可用、服务启用、运行健康分开；不把 pointer existence 当健康。

### B12 — P2：计划支持的选项不是当前可运行选项

`modules/proxy.go:30-31` plan 接受 block-proxy，但 `proxy/native.go:34-35` live compiler 拒绝。plan 提供 split/global/direct 和 dnsStrategy，live select (`proxy_runtime.go:149-159`) 没这些输入；`server.go:191-192` plan apply 返回 501。

**不存在隐蔽计划执行**：plan 明确 readOnly/canApply=false，本次 F03 强化了提示。建议 proposal-only 选项标未来/不可运行，或者仅展示与 live 能力匹配的预览；保留 plan id/generation 但不能当 live 代际。

### B13 — P2：capture active 是资源存在，不是数据路径健康；警告未投影到用户

`capture.go:126-136` argv 成功即 active；Reconcile 查资源存在，不查 DNS/节点/计数/offload；`proxy_capture.go:18-23` GET 吞 reconcile 错误仍 200。`proxy/firewall.go:169-176` 的 offload、encrypted DNS、存活 NAT DNS conntrack 警告不出现在 Status (`capture.go:21-29`) / API。

Cleanup 删规则不会清既有 DNS REDIRECT conntrack，不能保证立即 fail-direct/DNS 恢复。这在内部文档有边界，但用户确认只看一个地址和策略。

修复：installed / rules verified / data path verified 独立状态；显示实际目标范围、DNS/IPv6/offload/旧连接影响和撤销边界；精确单客户端 conntrack 管理需独立验证，不能全局 flush。任何接管测试须先由 root 向用户说明对象/时长/回滚并取得确认。

### B14 — P2：启停与开机期望状态是两个提交

`runtime.go:96-106` Start/Stop 先成功，再 persistDesired；失败只返回 storage_failed，进程已改变但 boot intent 可能相反。`:168-175` 还忽略除了读成功外的 ReadFile error。建议 partial-success status + 可重试保存目标、不重放启停，显示当前和开机意图的差异。

### B15 — P3：capture journal 缺父目录 fsync

`capture.go:221-246` file sync+rename 后没有 directory fsync；Cleanup unlink `:158-164` 同样缺。仅列 OS/storage/power failure 的 durability 限制；普通进程崩溃不会让已完成 rename 在运行内核中自动消失，也未复现 orphan rules。不要优先于 B1–B9。

### B16 — P2：错误码映射与 manager 实际名字不一致

API `configuration.go:136` 用 pending_confirmation/risk_ack_required，manager 发 confirmation_pending/risk_acknowledgement_required (`manager.go:229,445,494`)，因此本应 409 的冲突成 400。带 operation 的 commit error 一律 409 (`configuration.go:81-87`)，reload/rollback/storage failure 与其余 500 分类不一致。

修复：共享稳定错误类别 + 保留 operation；测试实际 code/status，前端按可恢复冲突/失败分类，不解析英语消息。

### B17 — P2：接管路由器 DNS 后，局域网名字不再走原 dnsmasq

capture `proxy_capture.go:64` 将 192.168.31.1 DNS 重定向；compiler 对 localhost/local/lan 名称用 dns-direct (`proxy/native.go:166`)，默认 dns-direct 是公网 223.5.5.5 TLS (`:81-83`)，不是原 LAN resolver。select 无本地 resolver 输入 (`proxy_runtime.go:149-159`)。DHCP hostname/私有记录不会查原 resolver。

修复：明确 LAN/local-domain resolver path 和 loop exclusions；“直连 DNS”不能等价“局域网 DNS”。fixture 验证本地域走原解析器，Internet 规则走对应上游。

### B18 — P2：同一事务新增跨文档引用无法正常暂存

Stage 只把当前候选配 live documents 给 validateNative (`control/manager.go:245`、`:302-313`)；新增 network interface + 新 wireless/DHCP/firewall 引用，依赖草稿会 invalid。Commit 在 combined validation 前先拒绝任何 stored invalid draft (`:467-468`)，即便合起来一致也不能 commit。

修复：draft bundle validation 与单文档语法验证分层，可对明确选中的 candidate set 校验；不要求中间 Commit 才能暂存依赖。验收新增接口+引用同代际一起 Commit，缺失引用仍拒绝。

## 6. 优先实施顺序 / 用户验收

1. **先保恢复安全：**B1、B2、B3、B5、B7、B8、B9。离线注入故障与并发 fixture，不碰真实路由器。报告/状态必须准确区分 accepted、applied、verified、rolled back。
2. **防丢编辑与普通设置：**F06/F07/F08/F09/F10。一次改 Wi-Fi、一次 DHCP/static lease、一次 WAN/管理地址流程，不要求用户读 UCI，也不靠两个中间 Commit。
3. **真实历史和图表边界：**按 durable-history 计划；F12/F13。刷新浏览器/关闭一天/重启后真实历史仍在；coverage gaps 保留；无一年数据时说从何时开始。
4. **代理务实 onboarding：**本次 F04 只是导向；继续做规则集可管理、已保存策略回填、local DNS、实际 connected 诊断，以及 B4/B6/B10/B12/B13/B14。不能因 UI 步骤齐全就宣布透明代理全域可用。
5. **官方 parity 分批：**优先实际高频 WAN/LAN/DHCP/Wi-Fi/端口/NAT/重启与备份，再 Mesh/MLO/双WAN/QoS 等；每项有发现→读取→类型化编辑→影响预览→应用→核验→撤销。参考官方矩阵，不猜硬件能力。
6. **体验收尾：**F11/F14/F15 和 B11/B16/B18。可深链任务、日期一致、手机版、读错/空态/禁用原因明确。

建议可复用用户验收脚本：

- “我想改 SSID”：从 Wi-Fi 找到可编辑当前值 → 返回观察不丢输入 → 暂存看差异 → 单次风险确认 → 新连接后可确认/恢复 → 结果真实。
- “我想找昨晚断网时的流量”：1d 范围 → 显示真实覆盖/空洞/起始时间 → total bytes 与 counters 对齐，不是速率求和。
- “我第一次用代理”：看清格式限制/依赖 → 获取校验核心 → 导入 → 看舍弃规则影响 → Commit → 启动 → 区分本地监听和外网连通 → 单客户端接管需要独立确认 → 可撤、状态可信。
- “我已有 frpc，回来改一个映射”：看到已保存服务器与映射，不出现假默认；只改一项，token 保留需要明确语义；保存代际/运行代际/远端 connected 分清。
- “我提交时断线”：固定 job 可读，操作 ID/当前 phase/截止时间仍可恢复；不能永远 pending，也不能在未知时说已回滚。
